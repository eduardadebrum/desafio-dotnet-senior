## Sintoma

ERPs de grandes tomadores recebem timeout em `ConsultarNfseServicoTomado`. O DBA aponta a consulta entre as que mais consomem banco no horário de pico. Já tentaram aumentar o timeout.

## Como reproduzir

Pelo teste, no commit do teste (anterior à correção):

```bash
git checkout e6b5c8c
dotnet test legado/tests/NotaCarioca.Testes.Integracao -f net8.0 --filter "ClassName~CH04Tests"
```

O teste executa a consulta pelo serviço e lê na `V$SQL_PLAN` o plano do cursor que a aplicação acabou de usar. Antes da correção ele falha mostrando `TABLE ACCESS FULL NFSE`.

Pelo banco, comparando as variantes da consulta com estatísticas de execução reais:

```bash
docker compose exec oracle sqlplus -s system/oracle_dev_123@//localhost:1521/FREEPDB1 \
  @/opt/nfse/db/evidencias/CH-04.sql 11444777000161 2026-08-01 2026-09-01
```

O script recebe documento do tomador, data inicial e data final. Precisa de um usuário que leia as visões `V$` (por isso `system`, e não `NFSE_OWNER`). No compose, o `NFSE_OWNER` precisa dos grants abaixo para o teste (o Testcontainers aplica sozinho):

```bash
printf 'ALTER SESSION SET CONTAINER=FREEPDB1;\nGRANT SELECT ON V_$SQL TO NFSE_OWNER;\nGRANT SELECT ON V_$SQL_PLAN TO NFSE_OWNER;\n' | \
  docker compose exec -T oracle sqlplus -s / as sysdba
```

## Causa raiz

A consulta fica em `NfseRepositorio.ConsultarServicoTomado`. O índice certo já existe: `IX_NFSE_TOMADOR_DT (TOMADOR_DOCUMENTO, DT_EMISSAO)`. Três detalhes da consulta impediam o uso dele, cada um por um motivo:

| # | Trecho original | Efeito |
| --- | --- | --- |
| 1 | `OracleHelper.P("doc", OracleDbType.Int64, ValidadorDocumento.ParaNumero(tomadorDoc))` | `TOMADOR_DOCUMENTO` é `VARCHAR2(14)`. Comparar coluna de texto com parâmetro numérico faz o Oracle converter a **coluna**: o filtro vira `TO_NUMBER(TOMADOR_DOCUMENTO) = :doc`. Com função sobre a coluna, o índice não serve para acesso |
| 2 | `/*+ FULL(n) */` ("hint pedido pelo DBA (2018)") | força a leitura da tabela inteira mesmo quando o índice é utilizável |
| 3 | `TRUNC(n.DT_EMISSAO) >= :ini AND TRUNC(n.DT_EMISSAO) < :fim` | função sobre a segunda coluna do índice: a data deixa de delimitar a faixa lida e vira filtro aplicado em todas as entradas do tomador |

O custo da consulta original é proporcional ao tamanho da `NFSE`, e não ao resultado. Na base local (2 milhões de notas) isso dá 0,6 s. Em produção, com centenas de milhões de linhas, é o timeout. Aumentar o timeout só mantém cada execução consumindo banco por mais tempo.

| 2 | PR-118: hint `INDEX`, parâmetro numérico | igual ao original: o hint não muda o plano, porque com `TO_NUMBER` na coluna o índice não atende o filtro | 167 mil | 0,62 s |

No sqlplus não existe variável de ligação do tipo data, então o script usa `TO_DATE(:ini, ...)`. O tipo que importa para o defeito (número contra texto) é reproduzido como na aplicação. O plano do cursor real da aplicação é o que o teste confere.

## Correção

Só em `legado/src/NotaCarioca.Dados/NfseRepositorio.cs`, método `ConsultarServicoTomado`:

```diff
-                "  -- hint pedido pelo DBA (2018)\n" +
-                "  SELECT /*+ FULL(n) */ " + Colunas + "\n" +
+                "  SELECT " + Colunas + "\n" +
-                "     AND TRUNC(n.DT_EMISSAO) >= :ini AND TRUNC(n.DT_EMISSAO) < :fim\n" +
+                "     AND n.DT_EMISSAO >= :ini AND n.DT_EMISSAO < :fim\n" +
-                OracleHelper.P("doc", OracleDbType.Int64, ValidadorDocumento.ParaNumero(tomadorDoc)),
+                OracleHelper.P("doc", OracleDbType.Varchar2, ValidadorDocumento.SomenteDigitos(tomadorDoc)),
```

Por que o resultado não muda:

- **Documento.** A coluna guarda 11 ou 14 dígitos, com os zeros à esquerda. Conferido na base local: 1.153.339 notas com 14 caracteres e 991.159 com 11, nenhuma com caractere não numérico. O serviço só chega ao repositório com documento válido (11 ou 14 dígitos), e `SomenteDigitos` preserva os zeros. Em produção, conferir antes do deploy com a consulta da seção [Impacto nos dados já gravados](#impacto-nos-dados-já-gravados).
- **Período.** `:ini` e `:fim` são datas sem hora (`ini.Date`, `fim.Date`). Para um limite à meia-noite, `TRUNC(d) >= :ini` equivale a `d >= :ini`, e `TRUNC(d) < :fim` equivale a `d < :fim`. O último dia do período continua excluído, como hoje (ver o README, em "O que ficou de fora").
- **Ordenação e paginação.** Não mudaram.

Depois, a evolução do CNPJ alfanumérico (`1868836`) trocou `SomenteDigitos` por `ValidadorDocumento.Normalizar` nessa mesma linha. Para documentos numéricos o valor é o mesmo (coberto pelo teste unitário `Normalizar_NumericosIguaisASomenteDigitos`), então o parâmetro continua texto e o plano não muda.

Sem migration: nenhum objeto de banco foi criado ou alterado.

## O que não foi feito

- **Timeout maior** (PR-118 sobe para 120 s): não ataca a causa e aumenta o tempo que cada execução ruim ocupa o banco.
- **Trocar o hint por `INDEX`** (PR-118): medido na linha 2, plano idêntico ao original. E hint fixo é o que criou o problema: sem hint o otimizador já escolhe o índice.
- **Índice novo ou índice por função** (`TO_NUMBER(TOMADOR_DOCUMENTO)`): exigiria construir um índice numa tabela de centenas de milhões de linhas para contornar um erro de tipo no parâmetro. Também quebraria com o CNPJ alfanumérico.
- **Corrigir o último dia do período excluído**: é um defeito diferente e muda o resultado que os clientes recebem hoje. Precisa de chamado próprio e de comunicado aos integradores.

## Impacto nos dados já gravados

Nenhum dado é alterado. Antes do deploy em produção, conferir a premissa do documento:

```sql
SELECT LENGTH(TOMADOR_DOCUMENTO) AS TAMANHO, COUNT(*) AS NOTAS,
       SUM(CASE WHEN REGEXP_LIKE(TOMADOR_DOCUMENTO, '^[0-9]+$') THEN 0 ELSE 1 END) AS NAO_NUMERICOS
  FROM NFSE
 GROUP BY LENGTH(TOMADOR_DOCUMENTO);
```

O esperado são só as linhas de tamanho 11 e 14. Se existir documento gravado sem zero à esquerda (por exemplo, 13 caracteres), a consulta antiga encontrava essa nota pela comparação numérica e a nova não encontra: nesse caso, normalizar esses registros antes (`LPAD`) ou tratar com a fiscalização. A consulta lê a tabela inteira: rode fora do pico.

## Risco da mudança

- O plano passa a depender das estatísticas, como qualquer consulta sem hint. Com estatística ausente ou muito defasada o otimizador pode escolher mal. Conferir em produção com a consulta 6 do script de evidência (coluna `ACESSO_NFSE`) depois do deploy.
- Tomador com muitas notas no período lê mais blocos, mas o custo fica proporcional ao que ele tem no período, não à tabela.
- A comparação numérica antiga deixaria de funcionar para todos quando existisse o primeiro tomador com CNPJ alfanumérico (`TO_NUMBER` de um valor com letra é `ORA-01722`). A comparação como texto elimina esse risco, e é o que permitiu a evolução do CNPJ alfanumérico usar a mesma consulta.
- Rollback: reverter o commit `58e7111`. Não há mudança de banco.
